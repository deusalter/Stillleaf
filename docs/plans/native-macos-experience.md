# Native macOS experience: implementation plan

Status: all three independent reviewers cleared exact plan `0bf658d`; the coordinator authorized execution. This document records the reviewed design and execution gates. No additional user approval gate is proposed.

Baseline: canonical `origin/main` at `471d297e11fe4efa239af0bb022a2964dee76e52` (PR #10 merge). Branch: `ui/native-macos-experience`. Preserve `reader/cloud-integration`, recovery refs and artifacts. Work and synthetic validation remain cloud-only; no access to the user's Mac, installed app, books, history or permissions.

## Outcome and boundaries

Deliver one coherent first release: a system sidebar and window toolbar, native EPUB window controls and appearance popover, consistent system controls in Settings and History, and short interruptible transitions. Retain Stillleaf's palettes, Pageleaf marks, covers, bundled fonts and quiet opaque reading surfaces. Liquid Glass belongs to navigation and control chrome on supported systems; it does not coat prose, charts, library cards, note excerpts or the whole window.

Keep the reading engine, native reading evidence and persistence architecture from PR #10. No locator migration, history rewrite, annotation schema rewrite, new permission requirement or scroll-driven glass/geometry animation. Retain EPUB's DOM selection popup, inline highlights, margin notes and existing content dialogs in this release; they require document-coordinate behavior and are not advertised as native glass. Migrating those editors to native views is outside this first release.

## Apple API evidence and compatibility

Official Apple documentation retrieved for this plan:

- [Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass): rebuild with the latest SDK, favor standard framework controls, remove custom chrome backgrounds that obscure system treatments, use custom glass sparingly, and test accessibility settings.
- [Applying Liquid Glass to custom views](https://developer.apple.com/documentation/swiftui/applying-liquid-glass-to-custom-views): `.glassEffect(.regular)` and `GlassEffectContainer` are genuine framework effects; excessive effects/containers can degrade performance.
- [`NSGlassEffectView`](https://developer.apple.com/documentation/appkit/nsglasseffectview), [`glassEffect(_:in:)`](https://developer.apple.com/documentation/swiftui/view/glasseffect(_:in:)), and [`GlassEffectContainer`](https://developer.apple.com/documentation/swiftui/glasseffectcontainer): Apple's symbol metadata explicitly gives **macOS 26.0** availability.
- [`NSVisualEffectView`](https://developer.apple.com/documentation/appkit/nsvisualeffectview): macOS 10.10+. This is an older native material fallback, not Liquid Glass.
- [`accessibilityReduceTransparency`](https://developer.apple.com/documentation/swiftui/environmentvalues/accessibilityreducetransparency) and [`colorSchemeContrast`](https://developer.apple.com/documentation/swiftui/environmentvalues/colorschemecontrast): macOS 10.15+, available within the current deployment target.

`Package.swift` has Swift tools 5.8 and `.macOS(.v13)`. Current `macos.yml` runs `macos-14` with no Xcode selection or SDK logging. PR #10's final PR job `110155947325` logged Apple Swift **5.10**, target `arm64-apple-macosx14.0`; the exact SDK version was not logged. That toolchain cannot be assumed to compile new APIs. `if #available(macOS 26, *)` protects runtime use but does **not** make unknown SDK symbols compile.

Implementation decision: keep macOS 13 deployment and existing compatibility job, add a macOS 26 / Xcode 26 job with explicit `DEVELOPER_DIR` and version/SDK logs. The published [GitHub macOS 26 ARM64 image inventory](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-arm64-Readme.md) lists Xcode 26.0.1 at `/Applications/Xcode_26.0.1.app` and macOS SDK 26.0. Start with that explicit version rather than a mutable default or preview. Verify runner label and path in an actual CI inventory step before introducing API-dependent product changes; image inventory alone is not execution proof. If the advertised version has moved, choose an available stable Xcode 26 version and record it explicitly.

Place new glass references in small `@available(macOS 26.0, *)` implementations under a compile-time toolchain guard validated in both jobs (Xcode 26's Swift compiler version must be confirmed before selecting the guard). Older SDK builds use system controls and `NSVisualEffectView` without parsing unknown API references. Modern builds select genuine glass only on macOS 26+, with opaque fallback for Reduced Transparency or increased contrast. No private API, dynamic class guessing or CSS blur impersonation. Standard native toolbars/popovers supply their system treatment; do not layer extra glass over them. One custom status-panel shell may use `NSGlassEffectView`; SwiftUI `glassEffect` is available if needed but is not a mandate to add more effects. Do not use `.clear` glass over text.

Compile modern SDK output with deployment target 13 and run fallback behavior on the compatibility OS as well as the older-SDK build. A macOS 14 run does not prove macOS 13 runtime compatibility: seek a supported cloud macOS 13 runner, otherwise report that precise runtime gap and verify availability/deployment metadata without claiming a 13 runtime pass. Neither raise the minimum OS nor silently drop the genuine glass layer if SDK provisioning fails.

## Motion, focus and accessibility

Use a common chrome motion policy in `ReadingMotion.swift`: 100–140 ms control feedback, 160–200 ms panel reveal/dismiss, and the existing 120 ms History result fade. Retarget/cancel in-flight state transitions; no sequential wait before accepting another command, overshoot, animation of content row heights, or delayed state commit. Native popovers/sidebar use system transitions. Web content-dialog reveal uses opacity/small transform after geometry is settled; closing must preserve draft guards and focus return. The new native chrome does not replace PR #10's page-slide/continuous scroll behavior.

Reduced Motion immediately suppresses custom animation and cancels active custom transitions without dropping the final state. Reduced Transparency substitutes solid chrome; increased contrast uses visible boundaries, selected/checkmark state and readable labels rather than color alone. Observe AppKit accessibility display-change notifications for native hosts and forward only policy flags to web dialogs, supplementing web media queries; do not assume web media queries express every Mac setting. Accessibility settings changing while a panel is open must update it without losing edits.

Keep system focus rings, VoiceOver labels/selected state, logical tab order, escape dismissal, and native Edit/Undo/Copy/Paste responder behavior. Menu equivalents and toolbar dispatch share one adapter: Command-F search; sidebar toggle in View; bookmark shortcut chosen without colliding with existing renderer shortcuts; Appearance and notes get labeled menu items. Test text-field/textarea focus so arrows, Space and shortcuts never turn pages while editing. Escape dismisses the topmost transient UI, then exits Focus only when no editor/dialog owns it. Store the initiating toolbar item for focus return, with web-content fallback if it disappears. Native chrome must not seize focus on acknowledgements.

Fullscreen, key/inactive window changes and Focus reading keep traffic lights/standard window recovery available. Do not animate reader viewport dimensions frame-by-frame when showing chrome: one settled layout change is routed through existing anchor-preserving relayout, and old pagination is invalidated truthfully. Minimize, multiple reader windows, display scale changes and moving between displays must not bind controls to another reader or grant activity credit.

Add consistent Settings (Command-comma) and Library commands to `AppPresence.swift`/`BooksPresenceApp.swift`, routed through existing `AppModel.showDashboard` requests from any reader or menu-panel entry; do not close the book or create a second dashboard. Reader-specific commands resolve the current key reader and remain disabled when no eligible owner exists. Bind native popovers/sheets to their owning window. Focus entering a control must not manufacture reading activity or bypass current active/key/minimized/visible-position eligibility; test key changes, panel interaction and return against the existing `EPUBReaderWindows` focused-reader/progress-delivery gates. Finalize pending position on real focus loss as today; never force a reader to remain eligible simply because it owns a panel.

Theme changes update chrome in place and preserve the focused control, insertion point and unsaved Settings/note text; retain the identity exceptions already asserted by `UISmoke.swift`. Sheet contents adapt to the available window height with scrolling and accessible footer actions; the smaller dashboard target is contingent on these compact-sheet gates, not merely changing the minimum-size constant.

## Quantitative cloud gate revision for review

The former three-pass synchronous benchmark does not establish settled async History or animation responsiveness. The new gate retains the canonical `471d297` baseline, overlays only the identical measurement harness/readiness callback on it, and runs baseline/candidate on the same macOS26 runner and fixture. Each scale has four counterbalanced batches of five measured samples, with two separately recorded warmups in each fresh process and fresh view/controller identity for each sample. Readiness is the actual prepared History content's `onAppear`, followed by final native layout/display. A main-run-loop observer plus timed explicit layout/display records the largest synchronous main-thread work segment per sample. Animations are disabled for this matched gate so preparation/framework work can be compared without assuming a virtual display's presentation clock.

CI fails if p95 settled latency or main-thread work exceeds baseline by more than 10%, with a bounded 5 ms absolute noise allowance for small values (`max(baseline×1.10, baseline+5 ms)`). The allowance accounts for 1 ms readiness sampling and shared-runner scheduling; it is explicitly proposed for review rather than an unreported relaxation. Raw twenty-sample distributions and the evaluated thresholds are uploaded, including on failure. Significant costs at 50 ms or above retain the exact 10% bound.

Candidate-native measurements additionally use twenty actual AppKit bookmark actions (after two warmups), measuring immediate pending/disabled feedback plus display and separately acknowledged button selection plus display, and twenty popover openings, waiting for `popoverDidShow` plus final layout/display. Gates are p95 ≤18.7 ms for bookmark action-to-pending-feedback (one 60 Hz frame plus 2 ms sampling tolerance), ≤250 ms for renderer acknowledgement and panel show, and ≤16 ms for button layout/display. `NSApp.sendAction` measures the actual toolbar action path without the artificial press dwell introduced by `performClick`; the existing smoke still invokes `performClick` independently. Normal animations remain enabled for popover measurements.

This revision measures app/main-thread readiness and framework work, not GPU presentation or optical glass. `displayIfNeeded` and a cloud window server cannot prove when pixels reach a physical display, so hardware animation frame timing, optical quality, actual13, physical multi-display and live VoiceOver remain explicit external gaps. The revision does not waive existing renderer geometry/scroll bounds, actor/cache/cancellation, native persistence, motion-policy or final independent-review gates.

The first execution measured renderer acknowledgement p95 at 65.4 ms, whereas post-ack button layout/display was 0.33 ms. A WKWebView command crosses an asynchronous process boundary, so acknowledged selection is not an idle native-frame measure. The concrete correction adds synchronous native pending/disabled feedback with duplicate suppression; selected state remains authoritative on acknowledgement. The revised bounded gate separates immediate feedback (18.7 ms) from completion (250 ms); deliberate delayed-resource tests retain the pending state and never fabricate success. A native held-transport regression verifies immediate feedback, no duplicate command, selection after acknowledgement, and failure cleanup. This distinction is explicit for review.

History's three navigation buttons use SwiftUI's system plain style: native command/focus/accessibility semantics without the AppKit-backed borderless style's repeated representable work in both responsive header variants. Two completed executions exceeded the original 10% p95 threshold with borderless controls; the threshold remains unchanged for the lighter implementation. This is a measured implementation adjustment, not evidence that the overall gate has passed.

The first lighter-History executions passed every main-thread work gate but had different single wall-latency misses (Week +0.70 ms, Month +4.45 ms beyond their 10% limits); baseline Day p95 differed almost threefold across hosts. To remove the baseline-first scheduling confound, the final matched gate runs four counterbalanced batches of five measured samples per scale/build in baseline-first, candidate-first, candidate-first, baseline-first order. Each fresh process has two warmups per scale, retained separately for audit. All twenty measured samples are retained in the aggregate, including tails; the p95 definition and exact regression limits are unchanged. Batch distributions, order, and warmups are uploaded. This bounded method revision requires actual execution and reviewer assessment; it does not declare earlier failed runs passed.

The counterbalanced execution still exceeded History limits. System shell, reader toolbar, Appearance and shared pickers remain native. No regression threshold is relaxed.
